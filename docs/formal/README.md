# Native worker lifecycle experiment

This is a bounded, executable model of Soho's native Core lifecycle, derived from the Go implementation, rather than a specification of a stronger desired API. The checked safety properties describe observations and actual guards. Two stronger diagnostic properties deliberately produce counterexamples: closing an unreported working worker can race with dispatch, and the internal reopen helper has a period with no roster row (see "Reopen scope" below: no native command reaches that helper today). No Go behavior was changed.

## Reopen scope

The reopen scenario models the internal helper `cmdReopen` (`internal/cli/reopen.go:18` `cmdReopen`), not a supported native command. On the native transport the entry guard refuses `reopen` before that helper runs: `Run` stops a known command that `hcCommandAllowed` does not list (`internal/cli/cli.go:262-264` `Run`), the allowed list omits `reopen` (`internal/cli/cli.go:574-606` `hcCommandAllowed`), and the call to `cmdReopen` is after the guard (`internal/cli/cli.go:482` `Run`). The refusal list in the test includes `reopen` (`internal/cli/transport_hc_test.go:39-47` `hcRefusedCommands`). Nothing here asks to enable native `reopen`. The scenario stays in the model because the helper's release-before-spawn order is a concrete interleaving worth checking; its counterexample (`NoReopenGap`) is a property of that helper, not an observed behavior of a supported native command.

## Bounds and assumptions

There are two orchestrator command slots, two terminal addresses, two names (the requested name and one conflict suffix), and four initial scenarios: two competing spawns, dispatch versus release, reopen versus dispatch (the internal helper described under "Reopen scope", not a native command), and dispatch followed by wait. Each command executes once, a busy send can retry once, a startup conflict can try one suffix, and the environment can change one terminal status once. Each scenario also explores the relevant initial idle/working/blocked/done status, assigned-task/report presence, ownership, force, close and active-collaboration combinations. Report polling saturates after three observations. These finite domains bound the graph naturally; there is no transition-depth constraint or temporal cutoff.

The two command slots interleave between reads, task-pointer publication, Core sends, closes, roster removal and replacement publication. Roster prune and append are separate actions because their Go calls are separately locked. Sending resolves the current terminal by name, while release retains the address it read. A terminal that reports `done` remains live and can receive another dispatch; an exited program, represented as gone/closed, is different. Core name allocation and conditional send are assumed atomic service contracts. This model checks Soho's use of those contracts; it does not verify the Core implementation in another repository.

The model selects the non-queue send path with `prompt_check_seconds > 0`, a supported native status provider, a successfully proven ready guard, and ordinary caller/configuration admission. Queue, amendment, disabled prompt checks, idle-only guard negotiation, provider-specific startup screens, ten conflict retries, unrelated names/sessions, actual socket framing, filesystem faults, crashes, close failures, registry cleanup, copy/process ownership, and configuration changes after preflight are abstracted away. Startup's unknown result conservatively represents a terminal that may have been created; it is preserved and not automatically retried or rostered. Confirmed blocked starts are published. Read snapshots combine several Go reads, so this experiment explores selected concrete races, not every filesystem/read interleaving.

The report is one stable nonempty file for the current task. Its identity checks and finite working timeout are abstracted to three successful polls, assuming clock progress and stable content. An active collaboration makes the report an artifact rather than completion, and refuses release even under force. Explicit orchestrator finalization can clear that ownership; finalization's evidence/verdict validation and collaboration phase transitions are outside this model. Dispatch in an active assignment assumes its separate participant/role authorization has passed. No action creates a new collaboration while a lifecycle command is already in flight.

Liveness is `EventuallyUnblocked => ((sent /\ report /\ ~active) ~> waitDone)` in the wait scenario under weak fairness of the polling action, where `EventuallyUnblocked` is `[]<>(~Blocked)` and `Blocked` is the target terminal reporting `blocked`. It assumes a stable report, advancing time, no redispatch/release, and either no collaboration or an explicitly finalized one. It also assumes the worker eventually leaves the blocked state: `WaitPoll` is disabled while the terminal is blocked, because the Go wait returns `pending` for a blocked terminal with a report (`internal/wait/wait.go:534-580` `reportAgentState`) and only the overall wait timeout, which the model does not represent, ends that command. The model therefore does not claim completion for a worker that stays blocked forever. It does not assert that an orchestrator eventually finalizes an active assignment or that a worker eventually writes its report. The model abstracts the finite report-working timeout (a positive `max`; `reportAgentState` also returns `done` at `internal/wait/wait.go:524-526` `reportAgentState` when the configured maximum is zero) as three successful polls. The fairness negative control witnesses the antecedent and shows that the result is not vacuous. The diagnostic property `ReportEventuallyObservedUnconditional` is the same formula without the assumption and fails: TLC finds a dispatched task whose report is written, then the terminal becomes blocked and stays so, with the wait never completing. It is not part of the safety configuration; run it by replacing the `PROPERTY` line of a copy of the configuration.

## Findings and explicit diagnostic expectations

`NoUnreportedWorkingClose` is expected to fail: this is a real defect in the lifecycle concurrency contract, supported by a model trace and Go inspection, not a native reproduction. Let release read an assigned worker as idle with no report, let dispatch publish/send a task so Core reports working, and then let release continue to `(*backend).Close`. Its earlier check is not repeated and `kill` has no status condition. The source is `internal/cli/release.go:84-123` `cmdRelease` plus `internal/hcbackend/backend.go:992-1002` `Close`; the roster lock at `internal/core/state.go:483` `RosterRemove` runs after closing and cannot protect this window. The diagnostic also admits the shorter environment-status-change trace; the automated diagnostic pins the external-change budget so that the counterexample specifically exercises two commands. A production fix would require an atomic service-side close condition or an appropriate lifecycle serialization design; choosing and implementing that fix is outside this experiment.

Status of that defect: the model still describes the commands as they were when it was written, without a shared lock, so the diagnostic keeps failing in the model. The code has since gained a per-worker lifecycle lock (`internal/core/worker_lifecycle.go`) that native `dispatch` holds from its roster read to its guarded send and native `release` holds from its roster read to the close; `release --force` closes regardless, as before. The model was not extended with that lock, so it does not prove the fix; the proof is the two-process regression test `TestReleaseHcConcurrentDispatchDoesNotCloseWorkingWorker`.

`NoReopenGap` is expected to fail. It describes the internal reopen helper only (see "Reopen scope": the native entry guard refuses `reopen`, so no native command shows this gap today). The helper's comments and order document it: `internal/cli/reopen.go:77-79` `cmdReopen` (the preflight observation does not reserve configuration or backend capability) and `internal/cli/reopen.go:96-114` `cmdReopen` (release completes before spawn). The trace is successful preflight, close old address, retire its row, then submit the replacement. At that boundary neither address has a roster row; a subsequent failed or uncertain replacement can leave that situation in place. The model retains this gap and checks successful preflight instead of inventing make-before-break behavior. “Replacement admitted” means local preflight, not a running or rostered replacement.

Every synthetic guard-removal failure is a deliberately incorrect model, not a newly discovered Go defect. The unmodified spec remains unchanged throughout mutation runs. An early development run attempted to index a gone target at address zero; that was a model error and was corrected with a total `Status` operator before the final checks. An early mutation-driver version lost TLA indentation, and another expected an older TLC temporal-error string; both harness problems were corrected and rerun. Preserved earlier logs are diagnostic history, not final evidence.

## Running and preserving evidence

Use the existing TLA tools jar and a Java runtime. No download, live `soho`/`hc` call, or dependency installation is needed. The Go runner accepts an absolute jar path and a new absolute evidence directory that must not already exist:

```text
go run docs/formal/check.go /absolute/path/tla2tools.jar /absolute/path/new-evidence-directory
```

For each experiment the runner creates an isolated working directory with `docs/formal/worker_lifecycle.tla` and its configuration, records their SHA-256 values, and executes the following command from that directory. This keeps TLC's generated `states/` files outside the source checkout:

```text
/usr/bin/java -XX:+UseParallelGC -cp /absolute/path/tla2tools.jar tlc2.TLC -workers 2 -config docs/formal/worker_lifecycle.cfg docs/formal/worker_lifecycle.tla
```

The runner enforces a 270-second deadline for each process, saves the complete output in `tlc.log` and its own status in `exit.txt`, and preserves the actual command in `command.txt`. It runs an unmodified safety/liveness control, ten independent action-guard removals covering the nine invariants, a fairness-removal control, both expected diagnostic failures, and another unmodified safety/liveness control. Each mutation uses a separate copied spec and checks the named semantic violation; parse errors never count as a kill. Both source and configuration must remain byte-identical. Every run and mutation is left in place for the owner to retain or clean up.

Recorded result of the runner with the `EventuallyUnblocked` assumption and the `~Blocked` guard on `WaitPoll`: exit 0 and the final line `PASS: ten independent guard removals killed for nine invariants; fairness removal killed; two diagnostic expectations witnessed; source and config unchanged; fair temporal controls completed before and after`. Both unmodified controls (`control-before`, `control-after`) printed `Model checking completed. No error has been found.`, `499996 states generated, 261501 distinct states found, 0 states left on queue.` and `The depth of the complete state graph search is 16.` The `ReportEventuallyObservedUnconditional` diagnostic, run once by hand with the same command on a copy of the specification and a configuration holding only that `PROPERTY`, printed `Error: Temporal property ReportEventuallyObservedUnconditional was violated.` and exit code 13 (its trace ends in a blocked terminal and stuttering).

The delegated report records the final run's full summary lines, bounds, source hashes, mutation results, trace narratives and evidence location. The final safety configuration has no error; the stronger diagnostic failures are explicit regression expectations of the experiment, not hidden assertions removed to claim the implementation is race-free.

## Assessment

The experiment paid for itself as a small concurrency review: it separated observation-based guards from conditional Core effects, exposed the release/dispatch closing window, and prevented the preflight step from being mistaken for atomic replacement. This is bounded formal evidence under stated service assumptions, not a proof of the Go implementation, its tests, or native behavior. A useful next candidate in this repository is dispatch task-pointer publication/restoration racing with retirement, including stale writes and two assignments. The PTY actor handoff barrier lives elsewhere and remains out of scope.
